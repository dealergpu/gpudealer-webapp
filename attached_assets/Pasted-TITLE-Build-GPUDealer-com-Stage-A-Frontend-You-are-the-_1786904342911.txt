TITLE: Build GPUDealer.com — Stage A Frontend

You are the senior frontend engineer responsible for building the initial production-quality frontend for GPUDealer.com.

==================================================
1. PRODUCT CONTEXT
==================================================

GPUDealer.com is an early-stage marketplace/discovery platform for used GPUs and AI hardware.

The long-term vision is:

GPUDealer → discover used GPU hardware → capture sellers → capture buyers/requesters → match supply and demand → eventually become a GPU procurement/dealer business.

DO NOT build a GPU rental/cloud-compute platform.

DO NOT try to replicate eBay.

DO NOT build payments, escrow, shipping, auctions, bidding, cloud GPU provisioning, or complex marketplace infrastructure in this stage.

The Stage A product has four core capabilities:

1. Browse/search existing GPU and AI hardware listings.
2. Sellers can register and list their own hardware.
3. Buyers can register and submit hardware requests when they cannot find what they need.
4. Registered users can manage their listings and requests.

The site should feel like a specialized, trustworthy marketplace for AI hardware rather than a generic classifieds site.

Think:

"Cars.com + PCPartPicker + marketplace intelligence for AI hardware."

The long-term brand promise is:

"Find. Sell. Request."

==================================================
2. PRIMARY USER FLOWS
==================================================

FLOW A — Visitor discovers hardware

Visitor lands on GPUDealer.com
→ searches for RTX 4090
→ filters by VRAM, price, condition, location
→ sees normalized listings
→ opens listing detail
→ clicks "View Original Listing" or "Contact Seller"
→ may be asked to register for certain actions.

Browsing must NOT require registration.

--------------------------------------------------

FLOW B — Seller lists hardware

Visitor clicks:

"Sell Your Hardware"

→ registration/login if unauthenticated
→ listing form
→ selects hardware category
→ enters GPU/server/memory details
→ pricing
→ quantity
→ condition
→ location
→ seller contact preferences
→ submits listing
→ listing enters pending/review state
→ seller sees it in dashboard.

--------------------------------------------------

FLOW C — Buyer requests hardware

Visitor clicks:

"Request Hardware"

→ registration/login if unauthenticated
→ request form
→ hardware requirements
→ quantity
→ budget
→ location/destination
→ condition preference
→ timeframe
→ optional notes
→ submit
→ confirmation
→ request appears in dashboard.

This request feature is extremely important.

It represents future GPU procurement demand.

Example:

"Need 32 × RTX 4090, used okay, <$1,300 each, ship to India within 30 days."

The system should capture this structured data.

--------------------------------------------------

FLOW D — Registered user dashboard

Dashboard should allow:

- My listings
- My requests
- Saved listings
- Profile/settings

Do not overbuild the dashboard.

==================================================
3. TARGET STACK
==================================================

Frontend:

- Next.js
- TypeScript
- App Router
- React
- Tailwind CSS
- Server Components where appropriate
- Client Components only where interactivity is needed

Backend is separate:

- Hono
- TypeScript
- Prisma
- PostgreSQL
- Supabase
- Cloudflare Workers

The frontend should communicate with the backend through a clean REST API.

Do NOT put business logic directly into the frontend.

Do NOT couple the frontend to Prisma/Supabase.

Create a small typed API client layer.

==================================================
4. DEPLOYMENT ASSUMPTIONS
==================================================

Frontend will ultimately run on Cloudflare-compatible infrastructure.

Optimize for:

- fast page loads
- SEO
- server rendering where useful
- minimal JavaScript
- good Core Web Vitals
- responsive design

Avoid unnecessary client-side state libraries.

Do not introduce Redux unless absolutely necessary.

Prefer:

- URL query parameters for search/filter state
- React state for local UI state
- server-side data fetching for listing/search pages

==================================================
25. SUCCESS CRITERIA
==================================================

A new visitor should understand GPUDealer within 5 seconds.

They should immediately understand:

"I can find GPUs."

"I can sell GPUs."

"I can request GPUs."

A seller should be able to create a listing in less than 3 minutes.

A buyer should be able to submit a hardware request in less than 2 minutes.

Search should be fast.

Pages should be SEO-friendly.

The UI should feel trustworthy enough for a $500–$100,000 hardware transaction.

Build cleanly enough that the next stage can add:

- direct seller/buyer messaging
- offers
- payments
- transaction fees
- verification
- procurement workflows
- dealer-assisted sourcing

without requiring a frontend rewrite.
